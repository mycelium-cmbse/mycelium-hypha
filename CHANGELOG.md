# Changelog

All notable changes to mycelium-hypha are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **A query API in `Hypha.Knowledge`** (`refs #194`), namespace `Hypha.Knowledge.Query`: the
  structural questions the skills and the metamodel-navigator agent answer today with `jq`,
  answered in C# from the same generated JSON, so the CLI and the coming MCP server share one
  implementation.
  - `IKnowledgeQuery`, for a language release: the installed releases and API versions, with
    which artifacts each has generated, subclasses (concrete or not), metaclasses with a feature typed by a type, a metaclass's full
    feature set with where each inherited feature comes from, redefinitions, an index entry, an
    element's cross-references, which elements' syntax fills in a feature, and a model-library
    declaration. For validating and citing, also: a metaclass's ancestors, whether one metaclass
    specializes another and through which supertypes, the OCL constraints and the operations that
    apply to a metaclass (its own and inherited, each naming where it is declared), an
    enumeration's literals, subsettings, the elements a grammar production builds, and the
    elements a specification clause treats (optionally with its subclauses).
  - Specification text: `Clause` returns a KerML, SysML or API clause with its verbatim text,
    grounded as `NORMATIVE`. The text needs the OMG PDFs, so when it was never generated the result
    is not an error but `Unavailable`, saying which commands generate it.
  - `Search` looks a text up across the metaclasses, the standard-library declarations and the
    clauses (by number or title), ranked as the lookup resolves names: exact, ignoring case,
    trailing part of a qualified name, then contains. A clause title counts as a name, so the clauses
    titled `Feature` rank with the metaclass `Feature`.
  - `HyphaAddress` names a generated page as `hypha://{tag}/{kind}/{name}` (kinds `metamodel`,
    `model-library`, `kerml`, `sysml2`), and `Resolve` turns an address into its page through the
    release's indexes, never a path given by the caller.
  - Structural queries (`fixes #209`), modelled on what uml4net's extensions and reports ask of a
    metamodel, all reading facts the generator wrote:
    - `Containers`: the composite features through which an element can be owned, typed by it or
      by one of its ancestors ("where can a `PartUsage` be nested?"). `FeaturesAccepting`: every
      feature that can hold a value of a type. Both list a feature once, where it is declared; with
      a `className`, only that metaclass's effective features, so a feature it redefines is left out.
    - `Neighbours`: the metaclasses its own features are typed by, and the features of other
      metaclasses typed by it.
    - `Package`: a package by qualified name or name (`Metadata` is two packages), with its
      metaclasses, its nested packages and every metaclass below it.
    - `EffectiveFeatures`: owned features and the inherited ones no feature of the metaclass
      redefines. `Opposite`: the other end of a feature's association, and the feature that
      redefines it in the metaclass, when one does.
    - `FeatureConstraints`: the constraints that name a feature among what they constrain; none
      does in the releases so far, since their constraints name their metaclass.
    - `Contributors`: the features that subset or redefine a feature, directly or through another
      contributor, each saying which, such as the 82 that contribute to `Namespace::ownedMember`
      (`EnumerationDefinition::enumeratedValue` by redefining `Definition::variant`).
  - `IApiQuery`, for a Systems Modeling API version: a PIM class, the cross-references of a type or a
    service operation, and a clause of the API specification.
  - Every result carries its grounding: the tier (`NORMATIVE`, `MODEL` or `DERIVED`), the release
    and the generated file it was read from, relative to the folder holding `knowledge/`. A name the
    release does not have is a normal result, not an exception.
  - Each document is read once, through its source-generated contract, and read again when its
    file changes, so a release regenerated by another process is not answered from stale memory.
    The cache (`IDocumentCache`) and the specification text reader (`ISpecificationReader`) are
    injected; `AddHyphaKnowledge` registers one of each, shared by both queries. Every read failure is a `KnowledgeLookupException`: a missing, unreadable (being rewritten),
    empty or malformed file, and one of the wrong shape, which the query contracts refuse instead of
    reading with members left `null`.
  - The release lookup, the query API and the API query choose a version and word their messages
    in one place, so the verbs those messages name are written once.
  - `KnowledgeQueryJqTests` checks every answer against the documented `jq` query on the committed
    golden metamodel and small fixtures; CI runs them with `HYPHA_REQUIRE_JQ`, so they cannot be
    skipped there.
  - `MetamodelJsonContext` now carries the camel-case naming policy of the file format, so
    `metamodel.json` and `index.json` read back through its default instance.
    `IKnowledgeLayout.MetamodelGraph` names `metamodel.json`, and `ModelLibraryFile.ReadIfPresent`
    reads the model-library index. `SpecificationIndex` is the shape of the `index.json` that
    `tools/spec-extract` writes, so the specification text is read through a contract as well.
- **The VS Code extension is on the Visual Studio Marketplace** (`refs #155`), as a preview
  pre-release under the `mycelium-cmbse` publisher: version `0.1.0` for Linux x64 and arm64.
  - The **Publish VS Code extension** workflow (`.github/workflows/publish-vscode.yml`), started by
    hand, packages each target and publishes it through Marketplace Trusted Publishing
    (`vsce publish --oidc`), so no Marketplace token is stored. A run waits for approval in the
    `vscode-marketplace` environment, and refuses to publish unless `tools/` matches the
    `tools-v<cli-version>` tag the bundled CLI is labelled with.
  - The extension has an icon, the Preview flag and a changelog of its own; `package.mjs` takes
    `--pre-release`, and `linux-arm64` is a package target. `@vscode/vsce` is 4.1.0, the first
    version with `--oidc`.
- **The VS Code extension for Windows x64** (`fixes #157`), validated end to end on Windows 11 and
  published with extension version `0.1.1` beside Linux x64 and arm64. CI now packages and
  smoke-tests the Windows VSIX too, against VS Code stable and against 1.100.0.
- **A release-operation lock in `Hypha.Knowledge`** (`fixes #166`), compatible with the VS Code
  extension's: the same `.release-operation.lock` file in the repository root, the same
  `{"pid", "token"}` content and the same recovery rules, so an operation that changes releases on
  its own (such as the coming MCP install) and an extension install never run at the same time.
  The CLI's own verbs do not take it, because the extension runs them while it holds the lock.

### Changed
- **`metamodel.json` 2.0.0: the generator writes the UML semantics, the query API reads them**
  (`fixes #208`). uml4net already computed them; the query API had been working some of them out a
  second time. **Regenerate every installed release** (`hypha generate --tag <release>`, and
  `hypha api generate --tag <version>` for an API version): a 1.0.0 document is refused with that
  advice.
  - `redefines` and `subsets` name the feature's owner, `{ "class", "association", "feature" }`,
    instead of a bare name, which several metaclasses share (66 of the 140 redefinitions in a release
    named such a feature). An end an association owns has `association` set instead of `class`.
  - New per attribute: `opposite` (the other association end; `null` when that end, or its
    association, has no name, as in the Systems Modeling API PIM), `isDerivedUnion`, `isUnique`,
    `isReadOnly` and `defaultValue`; per inherited attribute, `redefinedBy`, the feature that
    redefines it in that metaclass.
  - New per class: `inheritedOperations` and `inheritedConstraints`, as references to the declaring
    class's entry, each inherited operation with `redefinedBy`. Owned operations list what they
    `redefines`, and constraints their `constrainedElements`. The file grows from about 8 MB to
    about 16 MB; copying every inherited operation and constraint in full would have made it 26 MB.
  - `Constraints` and `Operations` read the inherited members from the document instead of walking
    the ancestors. `Operations` leaves out an inherited operation that the metaclass's context
    redefines, so it no longer lists two OCL bodies for one operation (such as `namingFeature` for a
    `ConstraintUsage`).
  - `Redefinitions` and `Subsettings` take an optional `owner`, after `tag` so a call written for the
    previous signature still means the release, and their results name the owner of the redefined
    or subsetted feature. `Features` returns the new facts. `Specializes` answers from
    the generated `allAncestors` (a metaclass conforms to itself) and returns `Specializes` as a
    field; the chain of generalizations stays as an explanation.
  - The metaclass pages link a redefined or subsetted feature to the page of the metaclass that
    owns it. A feature that redefines an inherited one of the same name used to link to itself.
  - The skills' and the metamodel-navigator agent's `jq` recipes follow the new shape.
- **`Hypha.MetamodelGen` is now `Hypha.Knowledge.Metamodel`** (`fixes #193`), the first step of the
  MCP refactor. Its test project is `Hypha.Knowledge.Metamodel.Tests`, and `AddHyphaMetamodelGen` is
  now `AddHyphaMetamodel`. The `tools/metamodel-gen/` folder keeps its name, and `Hypha.Knowledge`
  stays one library: reading and writing the knowledge are kept apart by namespace, not by project.
  - Every generated JSON document (the version manifests, cross-references, model library, the
    Systems Modeling API documents, `metamodel.json` and `index.json`) is written through a
    source-generated `JsonSerializerContext` beside its types, instead of reflection, and the
    documents the tools read back as typed objects are read through it too. `metamodel.json` and
    `index.json` are not read back as typed objects yet; that comes with the query API (#194).
  - The types `metamodel.json` and `index.json` are written in moved from the metamodel generator
    into `Hypha.Knowledge` (namespace `Hypha.Knowledge.Metamodel`), so code that reads them needs
    neither the generator nor uml4net.
  - `knowledge/metamodel.schema.json` describes `metamodel.json`, which until now was the one
    generated JSON document without a committed schema. `MetamodelSchemaTests` checks the produced
    document against it.
  - The file formats are unchanged: every generated document is written byte for byte as before.
- **`Hypha.Tools` on nuget.org has a proper package page** (`fixes #160`): a package readme, the
  Mycelium icon, project and repository URLs, copyright, release notes that link to the
  `tools-v<version>` GitHub release, and a description and tags that cover the Systems Modeling API,
  `lookup` and the JSON output. The repository README adds the command-line install from NuGet.
- CI and the publish workflow install the extension's dependencies with `npm ci --ignore-scripts`,
  so no dependency install script runs in a job that can publish.
- **CI runs once per pull-request commit** (`fixes #173`): *Build & Test & SonarQube* runs on pull
  requests and on pushes to `development` and `main` only (and by hand), instead of on every push
  as well, which ran everything twice. Every action the workflows use is updated to its current
  major version, pinned to a release at least two weeks old, and the .NET tools the workflows
  install (`dotnet-sonarscanner`, `dotnet-coverage`, `nuget-license`) are pinned. Dependabot now
  proposes weekly updates for the workflows' actions, the NuGet packages, the extension's npm
  packages and `tools/spec-extract`, grouped per ecosystem and only for versions two weeks old.

### Fixed
- The repository README no longer says spec citation needs a source checkout: since the uv-based
  specification generation, `hypha generate` builds the text itself.
- The extension's installed-VSIX smoke test finds VS Code's `cli.js` on Windows from 1.145 on, which
  keeps it under a folder named after the build's commit; it now asks the installation's own
  launcher (`bin/code.cmd`) for the path, and looks in both known layouts when it cannot.

## [2.3.0] - 2026-11-07

### Added
- **The Systems Modeling API & Services is part of the knowledge base** (`fixes #146`), as a body of
  knowledge with a version of its own beside the language releases:
  - **the PIM**: every type of the Platform Independent Model, in the shape of the metamodel pages
    (attributes with multiplicity, derivation, subsetting and redefinition, the full effective
    attribute set, and the six services with their operations). The `Data` interface and the `UUID`,
    `IRI` and `ISO8601DateTime` data types get pages too.
  - **the REST/HTTP PSM**: one page per API schema of the OpenAPI document, with required and
    nullable members and whether the endpoints use it as a request or a response model, plus every
    endpoint.
  - **the API specification text**, clause by clause, quotable through spec citation on the same
    terms as the KerML and SysML texts (generated locally from the PDF, never committed).
  - **`cross-references.json`**: PIM type ↔ specification clause ↔ PSM schema, the PIM members a PSM
    model leaves out, the PSM-only members, and the endpoint each PIM service operation maps to.
    Every edge names the method that produced it.
  - a new **`api-lookup`** skill, and the `spec-citation` and `version-management` skills now cover
    the API.
- **`hypha api discover | fetch | generate | list | use | remove`** install and manage an API version
  independently of the language releases, in `sources/api/<version>/` and `knowledge/api/<version>/`
  with a manifest of its own (`knowledge/api/versions.json`). An API version is a tag of
  `Systems-Modeling/SysML-v2-API-Services` that is also a language release, `2025-02` or later. The PIM model is the one
  input no repository carries; it is fetched from the OMG document server (`ptc/25-02-29`).
- **`hypha api list --json`** reports every installed API version, the default, and which of its
  artifacts (PIM, OpenAPI, cross-references, specification text) have been generated, in the same
  shape as `hypha list --json` with `versions` in place of `releases`.
- `python -m spec_extract --api-version <version>` extracts the API specification.
- **`hypha lookup`** resolves a metamodel or model-library name in an installed release and prints
  one page of its generated file (`fixes #153`). A name resolves exactly first, then ignoring case,
  then by a trailing part of its qualified name (`Real` for `ScalarValues::Real`); names that only
  contain the request are offered as candidates, never picked. A model-library lookup starts at the
  declaration rather than at the top of its package page. Hosts such as an editor extension use it
  instead of reading the generated indexes themselves.
- **`hypha list --json`** reports every installed release, the default, and which of its artifacts
  (metamodel, textual notation, model library, cross-references, specification text) have been
  generated.
- **`--toolchain-cache-root`** keeps the `uv` executable, uv's package cache and the Python it
  installs under one folder.
- **A VS Code extension for GitHub Copilot** (`extensions/vscode/`, `fixes #151`), a preview that is
  not yet on the Marketplace. A platform-specific VSIX bundles a self-contained `hypha` CLI, so
  nothing has to be installed by hand: on first use the CLI downloads `uv`, which provides the Python
  that specification extraction needs.
  - **Commands**: *Show Installed Releases*, *Check Available Releases*, *Install a SysML v2
    Release*, *Change Default Release* and *Remove a Release*. Installing asks for consent first,
    reports progress and can be cancelled; a release becomes the default only once it has been
    generated.
  - **Copilot tools**: `#hyphaReleaseStatus` reports the installed releases and which of their
    artifacts are present; `#hyphaLookup` resolves a metamodel or model-library name through
    `hypha lookup` and answers with a release-qualified source link, the candidates when a name is
    ambiguous, and one page at a time.
  - Releases, generated knowledge and the toolchain live in the extension's global storage, shared by
    every workspace on the same host. A lock file in that storage keeps two VS Code windows from
    changing releases at the same time.
  - Specification PDFs and extracted text are never packaged; they are downloaded and generated
    locally. End-to-end validation has been done on Linux/WSL; the Windows and macOS packages build
    but are not yet validated end to end.
  - `HYPHA_CLI_VERSION` sets the version the bundled CLI reports, so a VSIX built for publication
    names the hypha tools release it carries; any other build reports `0.0.0-dev`.

### Changed
- The `SessionStart` hook now provisions hypha tools `1.5.0` (`hyphaCliVersion`), which carries the
  CLI changes in this release.
- Every `--json` document (`check`, `list`, `lookup`, `api list`) is one line on standard output with no banner;
  log lines go to standard error, and every failure (including one before the verb runs, such as
  cancellation or an unreachable upstream) is written as `{"error": "..."}`.
- Bumped `uml4net` (`uml4net.xmi`, `uml4net.Extensions`, `uml4net.Reporting`) to `9.2.0`, which
  provides `QueryConstraintBody` and `QueryBodyConditionText` itself. The generators now use those
  and hypha's own copies in `ModelQueryExtensions` are gone (`fixes #145`); the generated knowledge
  is byte-identical.

### Fixed
- **`uv` is found in a wrapped archive.** The Linux and macOS `uv` archives keep the executable in a
  `uv-<target>/` folder, which the provisioner did not look in, so specification generation could not
  start there. Both the flat and the wrapped layout are now found, and an archive without the
  executable is no longer marked as verified.
- **`hypha remove` refuses a tag that is not a release**, whatever `knowledge/versions.json` lists.
  The tag names a folder that is deleted recursively, and `knowledge/api/` now sits beside the
  release folders, so a hand-edited manifest listing `api` could otherwise remove every installed
  API version.
- **The metamodel knowledge base now carries each operation's body OCL** (`fixes #143`). An
  operation's `bodyCondition` is a constraint the operation owns, not one of its class's rules, so
  the class-level constraint walk never reached it and every derivation body was dropped. Each
  `metamodel.json` operation now has a `body` (the OCL of its `bodyCondition`, empty when it has
  none) and its `documentation`, and element pages gain an **Operations** section with each
  operation's signature, documentation and body. On release `2026-05` all 99 body conditions come
  through, on the 39 metaclasses that own operations.

## [2.2.0] - 2026-10-05

### Changed
- The `SessionStart` hook now provisions hypha tools `1.4.0` (`hyphaCliVersion`), which carries the
  uml4net upgrade below.
- Bumped `uml4net` (`uml4net.xmi`, `uml4net.Extensions`, `uml4net.Reporting`) to `9.1.0` (tools
  `1.4.0`). Optional `[0..1]` enumeration properties are now nullable, so an unset `visibility`
  reads as `public`, the UML 2.5.1 default for a `PackageableElement`, and the generated metamodel
  keeps its exact shape. The only change to generated knowledge is in documentation text: every
  owned comment of an element is now used (8.x dropped all but one), and words on adjacent source
  lines are kept apart (e.g. `Elements. Note` instead of `Elements.Note`), which also changes three
  `index` summaries.
  Grammar references, textual notation, model library and cross-references are byte-identical.
- `ModelInspector` now selects interesting *classifiers*; the metaclass golden fixtures take its
  classes, so that set moved (8 metaclasses added, 6 orphaned golden files removed).

## [2.1.2] - 2026-09-07

### Fixed
- **The `SessionStart` hook no longer throws a raw PowerShell parse error on Windows without Git
  Bash** (`fixes #139`). Its dispatch shim is POSIX-shell-only (`case`/`esac`, `uname`), and Claude
  Code falls back to PowerShell for shell-form hooks when Git Bash isn't found, which can't parse
  it. The hook now pins `"shell": "bash"`, so Claude Code either runs it under Git Bash or reports
  a clear, dedicated "shell not found" error instead. That makes the project's existing Git Bash
  dependency explicit rather than reimplementing the OS/arch dispatch in a second language. No
  behavior change on Linux/macOS/Windows-with-Git-Bash, where bash was already the default.

## [2.1.1] - 2026-09-06

### Fixed
- **`/overview` no longer tells users to manually download the OMG spec PDFs or manually run
  `tools/spec-extract`** (`fixes #135`). Both are automatic now (`hypha fetch`/`hypha generate`'s `spec`
  artifact, #129); the command's own instructions had gone stale.

## [2.1.0] - 2026-09-06

### Added
- **`hypha generate`'s new `spec` artifact quotes verbatim OMG spec text without a maintainer source
  checkout** (`fixes #129`, tools `1.3.0`). `SpecGenerator` fetches and caches
  [`uv`](https://github.com/astral-sh/uv), which resolves or fetches a matching Python itself and runs
  `tools/spec-extract` (Python/pdfplumber) through it, with no pre-existing Python or provisioned `.venv`
  needed. A C# port of the pipeline was evaluated first (the PdfPig comparison spike, #128) and
  rejected: even after fixing a real bug, it still fell short of the mature Python pipeline's quality,
  and a port can at best tie Python, never beat it. `tools/spec-extract` also gained a real CLI entry
  point (`python -m spec_extract`) alongside its existing pytest-driven maintainer flow.

## [2.0.0] - 2026-09-04

### Removed
- **The committed knowledge floor** (`fixes #106`). `knowledge/2026-04/`, `knowledge/2026-05/`,
  `sources/2026-04/`, `sources/2026-05/` and `knowledge/versions.json` are no longer committed to git
  (2,120 files). Part 1 (`hypha use`/`remove`/`check`, below) landed the interactive mechanics while this
  floor still existed, so they could be verified before anything was deleted; this closes #106 by
  deleting it. A plugin install now fetches and generates *every* release identically, entirely on the
  user's own machine, on request, rather than two privileged releases pre-installed and everything else
  second-class.

### Changed
- **`.gitignore`, `CLAUDE.md`, `README.md`, `sources/README.md` and `knowledge/README.md`** rewritten
  for the no-committed-floor model (`fixes #106`): `/sources/*/` and `/knowledge/*/` are now
  root-anchored git-ignore patterns covering everything per-release, not just the OMG PDFs and their
  extracted text.
- **`Hypha.MetamodelGen.Tests` reads a committed test fixture instead of `sources/<tag>/xmi/`**
  (`fixes #106`): one real release's XMI is committed under
  `tools/metamodel-gen/Hypha.MetamodelGen.Tests/Fixtures/xmi/`, a fixture for this test project alone
  (`tools/` is never shipped with the plugin), so the generators still have real regression coverage
  without a network fetch or a reintroduced distributed knowledge floor. The accepted consequence:
  only that one fixture release is exercised, not every installed release, since nothing per-release
  is committed to loop over any more.
- **`KnowledgeRegenerationTests`, `MetamodelJsonGoldenTests`, `MetamodelJsonInvariantTests` and
  `PackageDiagramGoldenTests` redesigned** (`fixes #106`): with no committed `knowledge/<tag>/` left to
  diff against, `KnowledgeRegenerationTests` now fetches one release fresh and asserts two independent
  regenerations are byte-identical to *each other* (self-consistency, not a match against a
  human-reviewed baseline; a real reduction in rigor, named as such in its own doc comment); the
  metamodel-gen golden tests moved to the same committed-`Expected/`-fixture pattern
  `MetaclassFileGoldenTests` already used.
- **`hypha move-window`** (`refs #106`) is now documented and commented as the maintainer-only,
  source-checkout-only convenience it always functionally was, not a way to move a *committed* rolling
  window: its `--keep` count only ever governed which releases stay installed locally.

### Added
- **`hypha use`, `hypha remove` and `hypha check`** (`refs #106`) replace `hypha sync`: switching the
  default release, removing one no longer wanted, and comparing installed releases against what is
  offerable upstream are now separate, always-safe-to-run verbs instead of one verb that silently
  fetched and generated the newest release automatically.
  - The `version-management` skill gives Claude the vocabulary to list local vs. online releases,
    fetch a chosen tag with visible progress, switch the default, or remove one, always confirming
    with the user first, since fetching costs real time and removing is destructive.
  - `hypha fetch` downloads the OMG specification PDFs **by default** now (`--no-specs` to opt out):
    a fully local install needs everything a plain HTTP call can get it.

### Changed
- **The plugin's `SessionStart` hook only ever compares now; it never fetches or generates anything
  itself** (`refs #106`). `Hypha.Tools.Hook` runs `hypha check --json` synchronously (a couple of GitHub
  API calls, cheap enough that no background process is needed) and reports what it finds:
  nothing installed yet, a newer release available, or nothing to report, leaving the decision to
  fetch entirely to the user. The same hook also folds in what `hooks/check-spec-pdfs.py` used to do
  separately (naming missing OMG PDFs for the default release), so the plugin needs one
  `SessionStart` hook instead of two, and no longer depends on Python being present just to run it.
- **The `SessionStart` hook now also runs on `resume`, not only `startup`** (`refs #117`). A resumed
  session (`claude --resume`/`--continue`) used to skip the check entirely; `plugin.json`'s matcher is
  now `startup|resume`, so a long-running or resumed session still gets a fresh comparison against
  what's offerable upstream.

### Removed
- **`hypha sync` and the background/lock/status-file machinery it needed** (`refs #106`). Detached
  launching, a file lock, and a polled status file existed only because a hook-triggered fetch had to
  return immediately and report progress later; once fetching is something the user asks for and
  Claude runs in the foreground, none of that indirection is needed. `hooks/check-spec-pdfs.py` is
  retired, folded into `Hypha.Tools.Hook`.

### Added
- **`hypha`, a distributable command-line tool, is now what generates the knowledge base**
  (`fixes #81`). It ships as a `dotnet tool` for anyone with the .NET 10 SDK and as a
  **self-contained** executable per platform (`win-x64`, `linux-x64`, `osx-x64`, `osx-arm64`) for
  anyone with no toolchain at all, which is the answer #77 needed to the question of what happens
  when the toolchains are absent. NativeAOT is deliberately out of scope: Handlebars.Net compiles
  templates at runtime through expression trees, and uml4net is reflection-heavy over XMI.
  - Four verbs: `discover` (what the upstreams offer), `fetch` (download a release into `sources/`
    and record it), `generate` (the knowledge base) and `list` (what this checkout carries).
  - `generate` takes an optional artifact name, and the names are not a list it holds: they are the
    `Artifact` of whatever `IKnowledgeGenerator` implementations are registered, so adding a
    generator adds its verb and `generate nonsense` reports the ones that exist.
  - `ReleaseInstaller` gives fetching the orchestration generation already had: it downloads a
    release's inputs, resolves both upstream commits and merges the result into `versions.json`. The
    manifest is written only once the downloads finish, so an interrupted fetch leaves a release
    unrecorded rather than recorded and half-present.
  - A **Release** workflow packs the tool, publishes the four self-contained builds, generates
    `THIRD-PARTY-NOTICES.txt` for the bundled closure and drafts a `tools-vX.Y.Z` release. The tool
    and the plugin version independently.

### Changed
- **The tests no longer write the knowledge base; they verify it** (`fixes #81`). Running
  `dotnet test` used to rewrite `knowledge/`, which made every test run a write to the repository and
  made "is the working tree clean afterwards?" a check you had to remember to perform. Generation is
  `hypha generate`'s job now, and a test run leaves the working tree clean.
  - `KnowledgeRegenerationTests` regenerates the whole knowledge base into a scratch folder and
    compares it **byte for byte** against the committed files: the same determinism proof, without
    touching a tracked file. All 1,090 files match.
  - The seam is `HyphaKnowledgeOptions.OutputRoot` (the CLI's `--output`): inputs are still read from
    the repository, only the output moves. `knowledge/<tag>/spec/` stays on the input side, because
    the Python PDF chain writes it and the cross-references read it.
  - `Hypha.Knowledge.Tests` went from 30s to 3s, having stopped doing the generation work twice.
- **Generation orchestration moved out of the test fixtures and into the library** (`refs #92`). Each
  artifact is now an `IKnowledgeGenerator` (`Artifact`, `Order`, `GenerateAsync(tag)`), registered as
  a collection, so regenerating a release is a loop over `Order` rather than a list of calls each
  caller had to keep in step. The knowledge base comes out byte-identical.
  - `KnowledgeLayout` replaced three separate copies of the repository layout that had grown up in the
    test projects, one per project plus a private one inside a fixture.
  - Two fixtures now write the committed knowledge base instead of seven; the rest assert on scratch
    output, so changing one of them can no longer rewrite what ships.
  - Three invariants moved from assertions in tests into the generators, where they hold for every
    caller: a clause title must never reach the cross-references, two models must never slugify to the
    same example page, and the textual notation refuses to run before the metamodel index exists.
  - `HyphaKnowledgeOptions` replaces the optional parameters that were accumulating on
    `AddHyphaKnowledge` (token, API host, raw-content host, repository root, download concurrency),
    and is validated at registration rather than at first use. It is where the CLI's flags will land.
  - Every generator takes an `ILogger` and reports the same three messages, so a host can show
    progress without knowing which generator it is watching. That is the seam #77 needs.
  - `ReleaseDiscovery`, `CommitResolver` and `ReleaseFetcher` are resolved by interface like
    everything else.

### Fixed
- **The cross-references no longer degrade silently on a new release tag** (`fixes #96`). The PDF-free
  rebuild added in #88 carries title-matched clause edges forward from the committed document, which
  is lossless, except for a tag that has neither a clause catalog nor a previous document, where it
  wrote a file with roughly a third of its clause edges missing and nothing failing. `Build` now
  refuses that combination and names both ways out; `AllowGrammarOnly` states that a grammar-only
  document is intended.

### Changed
- **The cross-references moved to .NET, and no longer need the OMG PDFs** (`fixes #88`).
  `Hypha.Knowledge.CrossReferences` writes `knowledge/<tag>/cross-references.json` byte-identically to
  the Python it replaces, and this **completes the port** (`fixes #82`): .NET now produces every
  committed artifact.
  - **`cross-references.json` can be rebuilt from committed sources alone.** 351 of its 546 clause
    edges are stated outright by the grammar's own `// Clause` comments in the committed `.kebnf`;
    the remaining title-matched ones are carried forward from the committed document, which already
    holds them. A contributor without the specifications regenerates the file and gets the same
    bytes back; previously they could not regenerate it at all.
  - The licensing guarantee is unchanged and still tested: edges record clause **identifiers**,
    never clause text, which is what lets this file be committed while `knowledge/<tag>/spec/`
    cannot be.
  - `tools/spec-extract` is now the PDF chain and nothing else, and its README says so.
- **The textual-notation knowledge base moved to .NET** (`fixes #87`).
  `Hypha.Knowledge.TextualNotation` now writes `knowledge/<tag>/textual-notation/`: 309 example
  pages per release plus the index. All 618 committed example pages come out **byte-identical**; the
  only change is the line naming the generator in `index.md`.
  - Surface forms are still derived from the metamodel's own naming convention rather than curated
    (`PartDefinition` → `part def`, `PartUsage` → `part`), and still bounded by that release's
    metamodel index, so the mapping cannot invent an element.
  - The declaration match still refuses to fire inside an identifier or a quoted name:
    `counterpart` is not a `part`. Unlike the grammar patterns this one is deliberately left
    Unicode-aware, matching the Python it replaces: model text is user-written.
  - Example pages are ordered segment by segment and case-insensitively, which is what the committed
    index was generated with; an ordinal sort of the whole path would interleave folders with files.
- **BNF parsing and the grammar references moved to .NET** (`fixes #86`). `Hypha.Knowledge.Grammar`
  now parses both the textual `.kebnf` and the graphical `.kgbnf` and writes
  `knowledge/<tag>/textual-notation/grammar-{kerml,sysml,graphical}.md`. The generated files are
  **byte-identical** to what the Python emitted, apart from the line naming the generator.
  - The porting hazards are guarded by tests rather than left to be rediscovered: `\d` and `\w` are
    written out as explicit ASCII classes, because Python compiled these patterns with `re.ASCII`
    while .NET's shorthands are Unicode-aware; and the possessive quantifier on the clause number
    becomes an atomic group, which .NET does have.
  - The exclusivity guard is unchanged and still the point: a helper production shared by two
    elements contributes to neither. 96 of the 190 referenced helpers are shared, so relaxing it
    would report more feature assignments and mean less.
- **Release handling moved from Python to .NET** (`fixes #83`, `fixes #84`, `fixes #85`), into the new
  `tools/knowledge-gen/Hypha.Knowledge` library. `spec_extract.versions` and `spec_extract.fetch` are
  gone; `spec-extract` now does what it is best at (PDF extraction) and nothing else.
  - `ReleaseTag`, `ReleaseCatalog`, `GitHubToken` and `ReleaseDiscovery` offer the same 56 releases in
    the same order as the Python they replace; `VersionManifest` rewrites the committed
    `knowledge/versions.json` byte for byte.
  - `ReleaseInputs` decides *what* a release consists of as a pure function of a repository listing,
    so the selection rules are testable without the network; `ReleaseFetcher` downloads it.
  - Fetching is concurrent (6 at a time) over a pooled `HttpClient`. The Python fetcher opened a
    connection per file and was reset by the host after roughly 190 of a release's 314 files; a
    release now fetches whole in about 15 seconds.
- Well-established NuGet packages are now welcome rather than avoided, and services are composed
  through `Microsoft.Extensions.DependencyInjection`. `AddHyphaKnowledge()` registers one resilient
  named client (`Microsoft.Extensions.Http.Resilience`, so retries are **jittered**, which matters
  once downloads run concurrently) and the services that share it. This is groundwork for the CLI
  (#81).

### Added
- **Version awareness (`fixes #67`, `fixes #74`).** The knowledge base is now generated per upstream
  release tag (`YYYY-MM`) instead of from a single snapshot, with a committed rolling window of the
  two most recent releases, currently `2026-05` (the default) and `2026-04`.
  - `knowledge/versions.json` records the installed tags, the default, and the upstream commit each
    tag resolved to (traceability only; **the tag is the identifier**).
  - Release discovery offers a version only when the tag resolves in **both** upstreams: they are not
    in lockstep (`2023-07.1` is Release-only; `2024-08`, `2023-01`, `2026-05-pre` are Pilot-only).
    Tags are `YYYY-MM` with an optional point release; pre-releases, internal drops and letter
    revisions are excluded. 56 releases are currently offerable.
  - Fetching pulls a release's inputs from both upstreams, retrying transient connection resets with
    backoff and resuming a partial run.
  - Skills and subagents resolve the release from the manifest, answer from the default unless a tag
    is named, and **state which release an answer came from**.
  - `hooks/check-spec-pdfs.py` checks the default release and gives tagged download URLs.

### Fixed
- The previous inputs were not a coherent version: the PDFs resolved to Release tag `2026-03`, the
  textual sources to `2026-04`, and the metamodel XMI to an *untagged* `master` commit. Each release
  now comes from a single upstream point.
- `XmiModelReaderTests` was silently skipping on a stale `sources/xmi` path; it runs again.
- `.gitignore` gained a global `*.pdf` backstop. Moving the specs rule to the per-tag form stopped it
  matching a stale copy of the old layout, and three copyrighted OMG PDFs were very nearly committed.

### Changed
- `sources/` and `knowledge/` are laid out per tag: `sources/<tag>/{xmi,textual,specs}` and
  `knowledge/<tag>/{metamodel,spec,cross-references.json}`. `knowledge/textual-notation/` stays
  shared (hand-curated), and `sources/PrimitiveTypes.xmi` is shared: it is the OMG UML primitives
  library, published by neither upstream and identical for every release.
- The model URI inside the XMI (`…/SysML/20250201`) is no longer used anywhere as a version
  identifier. It tracks neither release nor content: the 2026-05 metamodel still declares a 2025 URI.
  The same model may appear under several tags, which is accepted rather than deduplicated.

### Added
- `knowledge/cross-references.json` (+ schema): edges from every metamodel element to the
  specification clauses that treat it, its BNF grammar production and any worked example. It records
  clause **identifiers only, never clause text**, so it ships even though `knowledge/spec/` cannot;
  185 of 187 elements resolve to at least one clause. Generated by the new `spec_extract.crossrefs`
  layer (`fixes #68`).
- Provenance tiers (`NORMATIVE` / `MODEL` / `DERIVED`) documented in the skills and the README, and
  carried in the data itself via the `provenanceTiers` block, so every cross-reference edge says how
  it was obtained.
- `knowledge/metamodel/diagrams/<Package>.md`: a Mermaid class diagram per package (41 files),
  generated from the XMI by the new `PackageDiagramGenerator` and linked from each package section of
  `knowledge/metamodel/index.md`. Each diagram carries the package's metaclasses (abstract ones
  marked), their generalizations, one-hop boundary nodes for supertypes owned elsewhere, and the
  structural owned features (`fixes #69`).
- Two rules keep those diagrams legible: derived features are omitted (computed views rather than
  structure, and they outnumber the structural features roughly three to one), and only
  metaclass-typed features become edges; primitive- and enumeration-typed ones are drawn inside the
  class box, so `String` and `Boolean` never become hub nodes.

### Fixed
- Packages that share a name across the two metamodels (`KerML::Kernel::Metadata` and
  `SysML::Systems::Metadata`) are merged into one diagram. Treating them separately wrote two files
  to the same path, silently discarding one of them.

### Changed
- `metamodel-lookup` and the `metamodel-navigator` subagent now query
  `knowledge/metamodel/metamodel.json` for set, closure and fan-out questions instead of grepping the
  per-element markdown, which stays the citable surface for single-element answers. Matching a JSON
  field is also exact, where grepping markdown matches documentation prose too.
- `spec-citation` degrades gracefully: without the OMG PDFs it now names the governing clause from

- `sysml-validation` grounds its reachability and multiplicity-bound checks in `metamodel.json`

  is decided.
- `jq` is now described as **recommended** rather than merely an accelerator, and the recommendation
  moved into the plugin-facing README; the previous note lived in `tools/metamodel-gen/README.md`,
